# 만드는 순서 (제안)

> 🟡 제안이다. 팀이 확인한 뒤 확정한다.
> 목표: 3명이 동시에 만들어도 같은 파일을 건드리지 않게 한다.
> 기준 문서: [PRD.md](./PRD.md)

## 한눈에 보기

| 단계 | 누가 | 무엇을 | 끝나는 조건 |
|---|---|---|---|
| S0 뼈대 | 1명 | 폴더 구조, 공용 파일, 데모 방, 배포 | 배포 URL에서 빈 화면 3개와 데모 방이 열린다 |
| 1라운드 | 3명 동시 | 방 만들기 · 수기 입력 · 보드 | 방 만들기 → 참여 → 지출 입력 → 보드 갱신이 30초 안에 된다 |
| 2라운드 | 3명 동시 | 방 규칙 · 캡처 인식 · 미제출 표시 | 캡처 한 장으로 보드가 갱신된다 |
| 3라운드 | 3명 동시 | 안내 페이지 · 정확도 측정 · 결과 카드 | 공모전 발표에 쓸 숫자와 화면이 나온다 |

## 나누는 원칙

1. **화면 흐름으로 3개 레인을 나눈다.** 방, 지출, 보드. 한 사람이 자기 레인의 화면, API, DB 조회까지 전부 만든다.
2. **자기 레인 폴더만 고친다.** 다른 레인의 파일은 읽기만 한다.
3. **공용 파일은 S0에서 한 번에 만든다.** 그 뒤로는 공용 담당 1명만 별도 PR로 고친다.
4. **레인끼리는 약속으로만 만난다.** 약속은 주소(URL), 테이블, 계산식 세 가지다.
5. **데모 방을 미리 넣어 둔다.** 방 레인이 끝나지 않아도 지출과 보드 레인이 바로 개발할 수 있다.

## 레인과 폴더

| 레인 | 담당 | 하는 일 | 건드리는 폴더 |
|---|---|---|---|
| 방 (room) | (이름) | 방 만들기, 참여, 방 규칙 | `app/rooms/` `static/rooms/` `tests/rooms/` |
| 지출 (expense) | (이름) | 수기 입력, 캡처 인식, 확인 화면 | `app/expenses/` `static/expenses/` `tests/expenses/` |
| 보드 (board) | (이름) | 남은 예산, 순위, 미제출, 결과 카드 | `app/board/` `static/board/` `tests/board/` |
| 공용 | (S0 담당) | 앱 시작 파일, DB 연결, 테이블, 공용 스타일, 배포 설정 | 아래 "공용 파일" |
| 문서 | (이름) | PRD, 이 문서, 발표 자료 | `docs/` |

**공용 파일** (공용 담당만 고친다):
`app/main.py` `app/db.py` `db/schema.sql` `db/seed.sql` `static/common.css` `requirements.txt` `render.yaml` `.gitignore` `.env.example` `README.md`

## 기술 스택 제안 🟡

| 부분 | 제안 | 이유 |
|---|---|---|
| 서버 | FastAPI (Python) | Claude API 인증키를 서버 안에 숨겨야 한다 |
| 화면 | HTML + JavaScript (빌드 단계 없음) | 설정이 적어 막힐 곳이 적다 |
| DB | 외부 Postgres (예: Supabase 무료) | 챌린지 기간 동안 데이터가 남아야 한다 |
| 배포 | Render 웹 서비스 | 수업에서 쓰는 방식 |

- 확인 필요: Render 무료 서버가 파일을 보존하지 않는지, Supabase 무료 요금제의 제한.
- 스택을 바꿔도 레인과 약속은 그대로 쓴다. 폴더 이름만 바뀐다.

## 약속 (contract)

### 주소

| 주소 | 화면 | 레인 |
|---|---|---|
| `/` | 방 만들기 | 방 |
| `/r/{code}` | 참여, 방 홈 | 방 |
| `/r/{code}/add` | 지출 올리기 | 지출 |
| `/r/{code}/board` | 남은 예산 보드 | 보드 |

API는 레인 이름으로 시작한다: `/api/rooms/...` `/api/expenses/...` `/api/board/...`

### 테이블

| 테이블 | 칸 | 쓰는 레인 |
|---|---|---|
| `rooms` | code, name, start_date, end_date, upload_cycle, deadline_weekday | 방 |
| `members` | id, room_code, nickname, budget | 방 |
| `expenses` | id, member_id, spent_on, merchant, amount, people, excluded, source, category | 지출 |

- 보드 레인은 세 테이블을 읽기만 한다.
- `source`는 `manual` 또는 `capture`다.
- 로그인이 없으므로 "나"는 브라우저에 저장한 멤버 id로 구분한다. 저장 이름은 `member_id:{code}`다.

### 계산식

- 내 몫 = `amount ÷ people`
- 쓴 돈 = 제외하지 않은 항목의 내 몫 합계
- 남은 예산 = `budget − 쓴 돈`
- 사용률 = `쓴 돈 ÷ budget`
- 순위 = 사용률이 낮은 순 (🟡 팀 확인 필요)

## 순서

### S0 뼈대 (1명)

- 브랜치: `feat/s0-<이름>`
- 만드는 것: 폴더 구조, 공용 파일 전부, 빈 화면 3개와 빈 API 3개, 테이블, 데모 방(`/r/demo`, 예시 멤버 3명과 지출 몇 건), Render 배포
- `requirements.txt`에는 뒤 라운드에서 쓸 패키지까지 미리 넣는다
- 끝나는 조건: 배포 URL에서 빈 화면 3개가 열리고, 데모 방 데이터가 DB에서 읽힌다
- 그동안 나머지 두 명: 테스트용 캡처 모으기, Claude API 인증키 발급과 캡처 1장 호출 확인, 1주 챌린지 시작

### 1라운드: 핵심기능 (3명 동시)

| 슬라이스 | 브랜치 | 끝나는 조건 |
|---|---|---|
| S1-방 | `feat/s1-room-<이름>` | 방을 만들면 링크가 생기고, 링크에서 닉네임과 예산을 넣으면 참여된다 |
| S1-지출 | `feat/s1-expense-<이름>` | 금액, 몇 명이서, 제외를 넣으면 저장된다 (데모 방에서 확인) |
| S1-보드 | `feat/s1-board-<이름>` | 멤버별 남은 예산 막대, 사용률, 순위, 초과 표시가 보인다 (데모 방 데이터) |

### 2라운드 (3명 동시)

| 슬라이스 | 브랜치 | 끝나는 조건 |
|---|---|---|
| S2-방 | `feat/s2-room-<이름>` | 기간, 업로드 주기, 마감 요일을 정하고 방 홈에 표시된다 |
| S2-지출 | `feat/s2-expense-<이름>` | 캡처를 올리면 출금 목록이 나오고, 확인 화면에서 몇 명이서와 제외를 고쳐 저장한다 |
| S2-보드 | `feat/s2-board-<이름>` | 마감까지 안 올린 멤버에 "미제출"이 표시되고, 마감 후 결과 카드가 나온다 |

S2-지출에 포함되는 것: 입금 무시, 가승인과 환불 제외, 기간 밖 날짜 제외, 중복 경고, 업로드 화면의 전송 안내, 캡처 미저장.

### 3라운드 (3명 동시)

| 슬라이스 | 브랜치 | 끝나는 조건 |
|---|---|---|
| S3-방 | `feat/s3-room-<이름>` | "무엇을 받고 무엇을 저장하지 않는지" 안내 페이지가 있고, 공용 스타일이 정리된다 |
| S3-지출 | `feat/s3-expense-<이름>` | 테스트 캡처로 금액 정확도, 걸린 시간, 카테고리 정확도가 숫자로 나온다 |
| S3-보드 | `feat/s3-board-<이름>` | 결과 카드를 이미지로 공유할 수 있다 (여유가 있으면 또래 평균 예산) |

3라운드에서는 S3-방만 `static/common.css`를 고친다.

## 충돌을 막는 규칙

- 작업을 시작하기 전에 `git pull` 한다.
- PR은 작게 만들고 하루에 한 번 이상 merge 한다.
- 공용 파일을 고쳐야 하면 단톡방에 먼저 말한다. 공용 담당이 별도 PR로 고치고 나머지는 pull 한다.
- 약속을 바꿀 때는 이 문서를 먼저 고친다.
- 실제 캡처와 `.env`는 커밋하지 않는다. 이 레포는 공개 레포다.
