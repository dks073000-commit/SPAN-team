## 나누는 원칙

1. **화면 흐름으로 3개 레인을 나눈다.** 방, 지출, 보드. 한 사람이 자기 레인의 화면, API, DB 조회까지 전부 만든다.
2. **자기 레인 폴더만 고친다.** 다른 레인의 파일은 읽기만 한다.
3. **공용 파일은 S0에서 한 번에 만든다.** 그 뒤로는 안정훈만 별도 PR로 고친다.
4. **레인끼리는 약속으로만 만난다.** 약속은 주소(URL), 테이블, 계산식 세 가지다.
5. **데모 방을 미리 넣어 둔다.** 방 레인이 끝나지 않아도 지출과 보드 레인이 바로 개발할 수 있다.

## 기술 스택 🟡

| 부분 | 제안 | 이유 |
|---|---|---|
| 서버 | FastAPI (Python) | 방 · 멤버 · 지출을 DB에 저장하고 보드를 계산해야 한다 |
| 화면 | HTML + JavaScript (빌드 단계 없음) | 설정이 적어 막힐 곳이 적다 |
| DB | 외부 Postgres (예: Supabase 무료) | 챌린지 기간 동안 데이터가 남아야 한다 |
| 배포 | Render 웹 서비스 | 수업에서 쓰는 방식 |

- 확인 필요: Render 무료 서버가 한동안 요청이 없으면 잠드는지(발표 직전에 미리 열어 둔다), Supabase 무료 요금제의 제한과 Render에서 접속되는 연결 주소.
- 스택을 바꿔도 레인과 약속은 그대로 쓴다. 폴더 이름만 바뀐다.

## 약속 (contract)

### 주소

| 주소 | 화면 | 레인 |
|---|---|---|
| `/` | 방 만들기 | 방 |
| `/r/{code}` | 방 홈. 보드가 먼저 보이고 그 자리에서 참여 | 방 (보드 부분은 보드 레인의 API를 쓴다) |
| `/r/{code}/add` | 지출 올리기 (계좌 연결, 확인 화면) | 지출 |
| `/r/{code}/board` | 남은 예산 보드, 결과 카드 | 보드 |

API는 레인 이름으로 시작한다: `/api/rooms/...` `/api/expenses/...` `/api/board/...`

가상 계좌 관련 주소 🟡 (지출 레인 안에서만 쓰므로 이태윤이 바꿔도 된다):

| 주소 | 하는 일 |
|---|---|
| `GET /api/expenses/virtual/accounts` | 고를 수 있는 가상 계좌 목록 |
| `GET /api/expenses/virtual/transactions?member_id=&account=` | 그 가상 계좌의 거래내역을 방의 기간에 맞춰 돌려준다 |
| `POST /api/expenses` | 확인 화면에서 고른 항목을 저장한다 |

### 테이블

| 테이블 | 칸 | 쓰는 레인 |
|---|---|---|
| `rooms` | code, name, start_date, end_date, upload_cycle, deadline_weekday | 방 |
| `members` | id, room_code, nickname, budget | 방 |
| `expenses` | id, member_id, spent_on, merchant, amount, people, excluded, source, ref, category | 지출 |

- 보드 레인은 세 테이블을 읽기만 한다.
- `source`는 `virtual`(가상 계좌), `manual`(직접 입력, 예비), `file`(파일 업로드, 선택) 중 하나다.
- `ref` 🟡 는 가상 거래의 고유 번호다. 같은 멤버가 같은 `ref`를 두 번 저장하지 못하게 해서 중복 저장을 막는다. 직접 입력은 비워 둔다.
- `category`는 비워 둔다. 카테고리화는 10/8 이후다.
- 로그인이 없으므로 "나"는 브라우저에 저장한 멤버 id로 구분한다. 저장 이름은 `member_id:{code}`다.

### 가상 계좌 데이터

- 파일 위치: `app/expenses/` 안 (지출 레인이 관리한다. DB 테이블이 아니다)
- 가상 계좌는 3개 이상 만든다. 멤버마다 다른 계좌를 고를 수 있어야 보드에서 차이가 난다.
- 날짜는 고정하지 않는다. "기간 시작 후 며칠째"로 적어 두고, 불러올 때 방의 `start_date`에 맞춰 실제 날짜로 바꾼다. 어느 방에서 시연해도 기간 안에 들어온다.
- 거래마다 넣을 것: 고유 번호, 며칠째, 상호, 금액, 입금/출금, 종류(일반 · 가승인 · 충전 · 내 계좌 이체).

### 환경변수

| 이름 | 내용 |
|---|---|
| `DATABASE_URL` | 외부 Postgres 연결 주소 |

실제 값은 Render와 각자의 `.env`에만 넣는다. 레포에는 이름만 있는 `.env.example`을 올린다.

### 계산식

- 내 몫 = `amount ÷ people`
- 쓴 돈 = 제외하지 않은 항목의 내 몫 합계
- 남은 예산 = `budget − 쓴 돈`
- 사용률 = `쓴 돈 ÷ budget`
- 순위 = 사용률이 낮은 순
- 초과 = 남은 예산이 0보다 작다
- 미제출 = 마감까지 그 주기에 저장한 지출이 없다

- 그동안 이태윤: 가상 계좌 3개의 거래내역 시나리오를 표로 적어 둔다 (PRD 6번의 시연 시나리오)
- 그동안 김경은: 보드 화면 구성 스케치 (단순화)

| 슬라이스 | 브랜치 | 만드는 것 |

### 합치기와 점검 (10/5 ~ 10/6)

- 10/5: 각자 PR을 main에 합치고, 배포 URL에서 전체 흐름을 한 번에 확인한다
- 10/6: 버그 수정. 새 방을 만들어 처음부터 끝까지 시연 순서대로 다시 확인한다
- 여유가 있으면 (우선순위 순): ① 화면에 "가상 계좌" 안내 문구 ② 은행 거래내역 파일 업로드 (은행 한 곳의 양식만)

## 충돌을 막는 규칙

- 작업을 시작하기 전에 `git pull` 한다.
- 자기 브랜치에서만 작업한다. main에 직접 push 하지 않는다.
- 완료하면 PR → 팀원 1명 확인 → merge. PR은 작게 만들고 하루에 한 번 이상 merge 한다.
- 공용 파일을 고쳐야 하면 단톡방에 먼저 말한다. 안정훈이 별도 PR로 고치고 나머지는 pull 한다.
- 약속을 바꿀 때는 이 문서를 먼저 고친다.
- `.env`와 실제 거래내역 파일은 커밋하지 않는다. 이 레포는 공개 레포다.
- 중간 보고 시점과 방식은 팀이 정한다 (예: 매일 저녁 단톡방에 한 줄).
